# 菜品与笔记统一搜索

## 契约与边界

新增搜索投影，不替换 `/dishes/search`、社区游标流或收藏投影。现有调用方保持原协议。新请求需要正常登录会话与 CSRF；访客可进行下述只读 POST 查询，受限申诉会话仍不可访问。

| 接口 | 用途 |
| --- | --- |
| `GET /api/v1/search/capabilities` | 返回已配置距离的食堂 ID、`WGS84` 与 `straight-line`，不返回设备位置 |
| `POST /api/v1/search/stalls/query` | 按档口分页，每组含食堂名称、档口评分及少量匹配菜品 |
| `POST /api/v1/search/dishes/query` | 同条件、指定 `stallId`，继续横滑时分页读取匹配菜品 |
| `POST /api/v1/search/notes/query` | 笔记搜索，保持当前用户点赞／收藏投影 |

统一请求字段：`q`（可空、最多50字符）、`diningHallIds`（多选）、`sort`、`page`、`size`。菜品增加 `minPrice/maxPrice/minRating/previewSize`；预览2–8条。笔记增加 `type=all/original/repost`。距离排序增加当次 `latitude/longitude`，必须成对且合法。

菜品排序为 `relevance/price_asc/price_desc/rating_desc/distance`；笔记为 `relevance/latest/likes/distance`。均使用服务端白名单和稳定 ID 打破同值，不接受 SQL 排序片段。菜品筛选继续保留未知价格或评分，常规排序置于完整数据之后；距离排序以真实距离为主、未知位置最后。综合排序优先名称完全匹配、前缀、包含；分组按组内最佳匹配菜品排序。组内预览沿用对应菜品排序。

分页总数为档口数或笔记数。先选档口页再取组内预览，避免同一档口散落多页；页码与总数、预览在同一只读可重复读事务中取得。菜品图片仅来自正式审核通过的菜品图片，不能用食堂／档口照片代替。档口标题可使用自己的封面。查询按页批量读取，不对每张卡片追加详情请求。

笔记只返回当前公开且未删除版本；关联位置沿当前启用菜品→启用档口→启用食堂计算。转发不借用原帖位置；未关联或关联失效时，不推断位置。选择食堂筛选时排除这些笔记，不筛选而按距离排序时置于末尾。搜索不受发现页置顶预留名额影响，不改变原社区信息流。

## 定位与可替换配置

`HallDistanceProvider` 隔离坐标来源与业务搜索。当前实现 `SearchLocations` 读取独立配置，无新迁移、不修改手绘地图轮廓。今后可替换为数据库坐标服务，搜索 DTO 和两端页面无需改变。

配置键为 `app.search.halls.<食堂UUID>.latitude/longitude/source`，坐标必须是核实后的 WGS84，`source` 必填，建议记录采集方法、日期和精度。例如在私有 YAML 中逐食堂配置：

```yaml
app:
  search:
    halls:
      "真实食堂UUID":
        latitude: ${HALL_WGS84_LATITUDE}
        longitude: ${HALL_WGS84_LONGITUDE}
        source: "实测日期、来源与精度"
```

这是配置形状示意，不能原样上线。默认没有任何预置真实坐标；手绘地图像素不能推算米数，同楼不同层可以配置同一个建筑入口位置。不要将 GCJ-02 或 BD-09 数值直接写入 WGS84 字段；先核对来源与坐标系。

距离采用球面直线距离，非步行距离、路线长度或步行时间。定位与请求均为临时数据：不写数据库、不放入 URL、不参与公共目录缓存、不新增位置日志。两端仅在点击距离排序后请求一次前台定位，12秒超时，设备精度超过1000米时不使用；5分钟后距离排序需重新定位。拒绝授权、无可用坐标或定位失败时保留原查询，仍能普通搜索。Android 暂停后取消正在进行的定位，没有后台定位权限或持续追踪。

## 两端交互

搜索共用“菜品／笔记”入口和本机按账号隔离的最近10条历史。菜品卡片一屏列数根据可用宽度2–6列计算，普通手机约4列；首批预取两屏、最多8条，右滑到末尾按相同筛选继续分页。已移除“全部 X 道匹配菜品”额外一行。单行名称不预留第二行空白，价格紧接名称；仍允许长名称最多两行。

筛选与排序独立；筛选编辑在“完成”后才应用，重置只清空面板草案，取消不改变已应用条件。菜品提供食堂／价格／评分，笔记提供食堂／原创或转发；无配送、优惠、人均消费等虚构条件。切换类型保留关键词与食堂，类型专有条件隔离。查询变化回到第一页；翻页保留筛选。客户端仅校验基础输入，正式权限与可见性始终由后端执行。

## 验证与部署

`UnifiedSearchIT` 使用专用 PostgreSQL/Redis、HTTP会话与CSRF验证分组分页、图片、未知值、隐藏链、笔记类型与距离、输入和未认证访问；`SearchLocationsTest` 验证距离与坐标。客户端分别有请求竞态、面板与横滑加载、瞬时定位、断授权和模拟器界面验证。浏览器／模拟器夹具不等于生产或 Redmi 定位实测。

需要先部署此后端再更新客户端。食堂真实坐标尚未完成采集与校准；默认只启用普通统一搜索，距离按钮给出位置待补充提示。本轮没有发布新版本或部署服务器。


## 搜索体验与缓存补齐

顶部交互控件与同一背景融合；档口及菜品名称单行省略，详情保留完整名称。金额使用普通十进制文本，不显示科学计数法。清空输入立即返回历史与推荐，非空编辑时延迟250毫秒获取真实名称建议，忽略迟到响应；提交结果与建议对关键词进行纯文本高亮。

不含位置的菜品查询使用 `GET /search/stalls`、`GET /search/dishes`，接入原有本地ETag副本与服务器目录修订缓存。每次访问先轻量校验，未变化时304复用本地数据；服务端只读取目录修订号，避免重复多表分组查询。已提交目录变更立即使投影失效。含定位仍走原POST且不缓存，笔记含个人状态仍沿用原读取逻辑，不加入公共目录缓存；Web沿用100MB上限，Android按访问写入，不全量预取。需先部署配套Backend。
